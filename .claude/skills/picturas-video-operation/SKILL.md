# Adding or changing a video operation in PictuRAS

Read `AGENTS.md` first: it describes the layers of UC-VID-001 (upload), UC-VID-003 (frame
extraction) and UC-VID-004 (trim). A new operation follows the same layering. Do not invent a
new microservice for an MVP operation unless the requirement needs separate scaling.

## 1. Pin down the requirement before coding

- Identify the use case (`UC-VID-nnn`), its business rules (`RNk`) and the requirement IDs
  (`REQ-VID-{FUNC}-nnn`) from the requirements document. Ask the user if they are missing;
  never invent numeric limits.
- List every limit per profile (anonymous / free / premium): source size, resolution,
  duration, frames, concurrent tasks, daily operations. Shared rules (RNG-nn) apply to all
  operations: 1 daily operation per video operation for registered users, premium unlimited,
  anonymous users blocked from video.

## 2. Layers to touch (in this order)

1. `imageStorageService/models/videoTask.js` – reuse `VideoTask` with a new `type`. Persist
   `userType` and `chargedOperation` on creation; workers must never guess the plan.
2. `imageStorageService/route/videos.js` – revalidate everything server-side: ownership filter
   (`ownerFilter`), `status === "ready"`, container + codec from `video.metadata`, plan limits,
   timestamps (`0 <= start < end <= duration`), concurrent-task limit. Return 400 for invalid
   input, 404 for missing/foreign videos, 429 for concurrency. Declare `/:userId/tasks...`
   routes before `/:userId/:videoId`.
3. `imageStorageService/services/<name>Worker.js` – serial in-process queue like
   `videoTrimWorker.js`: download to `os.tmpdir()`, run `ffmpeg` with `spawn` (no shell),
   10-minute timeout, 1 automatic retry, check the cancellation set between steps, clean
   temporary files and orphan S3 objects in `finally`/`catch`.
   Refund with `refundTaskOperation(task)` and check quota with `videoStorageQuota(task.userType)`
   from `services/videoTaskBilling.js` – the refund is idempotent, so both the cancel endpoint and
   the worker may call it.
4. `apiGateway/routes/videos.js` – `auth.checkToken`, `loadUser` (authoritative plan), reject
   anonymous, provisional charge `GET users:10001/:user/process/1` for non-premium, forward
   with `userType` from `users` (never from the body), refund on forward failure.
5. `frontend/lib/videos.ts` (API client), a dialog in `frontend/components/`, and task tracking in
   `frontend/providers/video-task-provider.tsx`. Use `/api-gateway/` via `frontend/lib/axios.ts`,
   UI primitives from `frontend/components/ui/` and the shared toast hook.
6. `docker-compose.yaml` for new env defaults; `README.md` and `AGENTS.md` for the new layer list.

## 3. Rules that must not regress

- Never trust client MIME type, extension, size or plan. Never buffer a whole video in Express.
- S3 keys are generated by the server (`videos/<uuid>.<ext>`); the original name is metadata.
- Video uploads never call the daily-operation endpoints.
- Every failure or cancellation of a charged task ends with exactly one refund.
- Comments reference the requirement they implement, e.g. `// RN3, REQ-VID-TRIM-NF03: ...`.

## 4. Done means tested

Use the `picturas-video-tests` skill: add route tests for every validation branch, worker tests
with real ffmpeg for the happy path, retry, cancellation and cleanup, and gateway tests for
auth/charge/refund. Then run:

```bash
cd imageStorageService && npm test          # ffmpeg suites skip locally without ffmpeg
cd apiGateway && npm test
docker compose build img_storage && docker compose run --rm --no-deps img_storage npm test
cd frontend && npm run build
```

Finish by updating `docs/testes-fase1.md` (test → requirement → result) and report to the user
which requirements are implemented, partial or not implemented.
